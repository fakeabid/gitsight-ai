Your .NET application should treat the Python service as an AI Review Service with a clear API contract. Your .NET code shouldn't need to know whether they use LangGraph, Gemini, NVIDIA, multiple models, chunks, agents, etc.
The important thing is to define the contract correctly before they implement it.

3. What the Python developer should be responsible for
This is the important part.
The Python developer shouldn't simply build:

    ↓
Gemini
    ↓

They should build an AI review engine.
4. Requirement #1 — Large PR handling
This is one of the most important requirements.
The Python service should not assume that the entire PR can be passed to the LLM in one request.
For example:
1500 changed lines
        ↓
Preprocessor
        ↓
Determine logical review units
        ↓
Chunk/context management
        ↓
LLM analysis
The splitting should ideally be based on logical code boundaries rather than blindly doing:
line 1–300
line 301–600
For example:
UserController.cs
UserService.cs
UserRepository.cs
may need to be considered together because they form one execution path.
5. Specialized analysis
This is where LangGraph becomes useful.
The graph can have nodes such as:
PR Input
   ↓
Preprocessor
   ↓
 ┌──────────────┬──────────────┬──────────────┐
 ↓              ↓              ↓
Bug Analysis  Security       Performance
              Analysis       Analysis
 ↓              ↓              ↓
 └──────────────┴──────────────┘
                 ↓
             Aggregator
                 ↓
           Deduplication
                 ↓
             Validator
                 ↓
            Final Output
But don't force every PR through every expensive node.
The graph can decide:
Database changes?
     ↓
   YES → performance/database analysis
or:
No security-sensitive changes
     ↓
Skip expensive security analysis
That reduces unnecessary LLM calls.
6. API failures must be handled on his side
This is extremely important.
Suppose Gemini returns:
429 Too Many Requests
The Python API should not simply crash and return 500.
The service should have a failure strategy.
For example:
LLM call
   ↓
Success?
 ┌───────┴───────┐
YES              NO
 ↓                ↓
Continue       Identify error
                  │
          ┌───────┼─────────┐
          ↓       ↓         ↓
         429    Timeout    5xx
          ↓       ↓         ↓
       Backoff  Retry      Retry
Then potentially:
Primary model unavailable
        ↓
Fallback model/provider
        ↓
Continue review
7. Rate limiting
This should not be your .NET application's responsibility.
The Python service should control how many LLM requests it makes.
For example:
PR 1 ─┐
PR 2 ─┤
PR 3 ─┼──→ AI Queue / Worker → LLM
PR 4 ─┤
PR 5 ─┘
Rather than:
PR1 ──┐
PR2 ──┤
PR3 ──┼──→ Gemini simultaneously
PR4 ──┤
PR5 ──┘
          ↓
        429
This is especially important once GitSight receives multiple webhook events.
8. Retries need to be intelligent
Tell him not to blindly retry everything.
For example:
429
Retry with exponential backoff / provider-specified retry delay.
attempt 1
 ↓
429
 ↓
wait
 ↓
attempt 2
 ↓
429
 ↓
wait longer
500/503
Retry may make sense.
Invalid request
Don't retry indefinitely.
400 Bad Request
      ↓
Fix input
Retrying won't fix it.
Authentication/API-key failure
Don't repeatedly retry.
401/403
 ↓
configuration/provider issue
 ↓
controlled failure
9. The service should never return random LLM text
This is another major requirement.
Your .NET application should not receive this:
The code has several issues...
1. blah blah
2. blah blah
and try to parse it.
The Python developer should define a schema.
For example:
{
  "reviewId": "abc123",
  "status": "completed",
  "summary": {
    "totalIssues": 3,
    "critical": 1,
    "high": 1,
    "medium": 1,
    "low": 0
  },
  "issues": [
    {
      "file": "AuthService.cs",
      "startLine": 42,
      "endLine": 45,
      "severity": "High",
      "category": "Security",
      "title": "Missing authorization check",
      "description": "....",
      "suggestion": "....",
      "confidence": 0.94
    }
  ]
}
And the Python service should validate the model output against that schema before returning it.
10. Hallucinated line numbers
This is especially important for GitSight.
The AI might say:

Lines 20–80
The Python service should validate findings.
For example:

line 150

        ↓

Diff contains:
20–80

        ↓

        ↓

discard / re-evaluate
This can dramatically improve the quality of your UI.
11. False-positive validation
This should be part of the Python developer's design.
Example:
Analyzer
   ↓
"Potential null reference"
   ↓
Validator
   ↓
Look at surrounding code
   ↓
Actually possible?
   ├── YES → keep
   └── NO → discard
This is one of the strongest reasons to use the graph.

I would strongly recommend that your contract supports something like:

15. What happens if the AI completely fails?
Your Python service should not take down your .NET application.
Example:
Gemini
 ↓
429
 ↓
retry
 ↓
429
 ↓
fallback
 ↓
fallback unavailable
 ↓
Review status = failed/retryable
Python returns:
{
  "status": "failed",
  "errorCode": "AI_TEMPORARILY_UNAVAILABLE",
  "retryable": true
}
Your .NET app stores:
Review Status: Retry Pending
rather than:
Application crashed
16. Security between your services
Because the Python service is hosted publicly on Render, don't leave the endpoint open.
Your .NET service should send something like:
Authorization: Bearer <internal-service-token>
Python validates it.
Also:
Don't send GitHub OAuth tokens to Python unless they're actually required.
Ideally:
.NET owns GitHub credentials
Python receives only the code-review data
And the LLM provider keys remain only in the Python environment.
17. Your contract with the other developer
I'd give the Python developer requirements along these lines:
Input
POST /api/reviews
Accept:
repository
PR number
PR title
changed files
patches/diffs
optional metadata
Processing
The service must:
Validate input.
Handle large PRs through context/chunk management.
Use LangGraph for controlled review orchestration.
Separate review concerns where beneficial.
Aggregate findings.
Deduplicate findings.
Validate findings against the actual diff/source context.
Validate final output against a strict schema.
Handle LLM rate limits.
Handle transient provider errors.
Implement bounded retries/backoff.
Support provider/model fallback where available.
Prevent excessive concurrent LLM requests.
Never expose raw provider errors to the client.
Output
Always return predictable JSON:
completed
failed
queued
processing
with standardized error codes.
18. What YOU need to implement in .NET
Your side should then be relatively clean:
ReviewController
       ↓
ReviewService
       ↓
AIReviewClient
       ↓
HTTP
       ↓
Python service
Create a dedicated client:
public interface IAIReviewClient
{
    Task<AIReviewResponse> AnalyzeAsync(
        AIReviewRequest request,
        CancellationToken cancellationToken);
}
Don't put:
HttpClient.PostAsync(...)
directly inside your controller.
Your controller shouldn't know anything about LangGraph.
The most important separation
Think of it like this:
Your .NET application
"I need this PR reviewed."
Python AI service
"I'll figure out how to review it reliably."
Your application shouldn't care whether the Python developer uses:
Gemini
DeepSeek
NVIDIA
OpenAI
LangGraph
5 nodes
20 nodes
chunking
fallback
Your contract is simply:
PR data
    ↓
AI Review Service
    ↓
Reliable structured review
That is the architecture I'd recommend for your team.
And yes, the large-PR handling, LLM rate-limit recovery, retries, fallback, chunking, LangGraph workflow, output validation, and AI-specific failure handling should primarily be implemented on the Python developer's side. Your .NET side should still have network timeouts, cancellation, and graceful handling of the Python service being unavailable, but it shouldn't be responsible for managing Gemini/NVIDIA behavior.
